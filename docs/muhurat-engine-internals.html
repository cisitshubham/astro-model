Panchang Engine · Endpoint 6

Muhurat Engine Internals

How /api/moohrats/ decides which dates in a month qualify as auspicious, and which clock windows it returns for them — traced through the code as it stands today.

GET /api/moohrats/ views.py 815–1076 Class GlobalMoohratsAPIView Ephemeris Swiss / Lahiri sidereal
The single most important thing about this endpoint: the date and the time are decided by two completely independent mechanisms. They never consult each other.

The date — rule-filtered

Each day of the month is tested against three astrological gates for the requested muhurat category. Pass all three and the date appears in the response.

The time — category-blind

The clock windows are the day's auspicious Choghadiya slots, derived only from weekday and sunrise/sunset. Every category on a given date gets the identical time list.

§ 1

Request contract

The endpoint is month-scoped, not day-scoped. One call evaluates every calendar day of the requested month.

# All 11 categories, default location (Ujjain)
GET /api/moohrats/?month=11&year=2026

# One category, explicit location
GET /api/moohrats/?month=November&year=2026&title=vivahmuhurat&location=Mumbai

# Several categories — repeat the param, or comma-separate
GET /api/moohrats/?month=11&year=2026&title=vivahmuhurat,mundanmuhurat
month
Required. 1–12, a full name (November), or an abbreviation (Nov). Case-insensitive.
year
Required. Integer, bounded to 1900–2100.
title
Optional. Lowercase, no spaces or slashes. Omit it and all 11 categories are computed. Accepts repeated params and comma-separated lists.
location
Optional. Free-text city, geocoded via Nominatim and cached 30 days. Falls back to Ujjain silently on failure.

Note also that unlike the other five endpoints, this response carries no date or location echo; the caller cannot tell from the payload which coordinates the times were computed for.

§ 2

The computation pipeline

Six stages, in the order the code executes them. Stages 1–2 run once per request; stages 3–6 run once per calendar day.

1Once

Validate, then resolve the observer

views.py:934–1022

Month, year and title slugs are validated first. Then geolocation runs through the shared GeoLocationMixin, which expects a date query param the caller never sent — so the view temporarily writes one in, resolves, and restores the original query dict:

request.GET["date"] = f"{year}-{month:02d}-01"   # synthetic
geo_data = self.resolve_location_and_tz(request)
request.GET = original_get                       # restored

This yields lat, lon and a single numeric UTC offset numeric_tz. Defaults on any failure: Ujjain, 23.1765°N 75.7885°E, UTC+5.5.

2Once

Arm the ephemeris

views.py:1021–1022
swe.set_sid_mode(swe.SIDM_LAHIRI)
calc_flags = swe.FLG_SWIEPH | swe.FLG_SIDEREAL

All longitudes below are sidereal, Lahiri ayanamsa — the standard Indian civil almanac convention. Swapping the sid mode would shift every nakshatra and tithi boundary.

3Per day

Sample Sun and Moon at local noon

views.py:1024–1033

The day is reduced to a single instant — 12:00 local time — converted to UT and turned into a Julian Day:

target_dt = datetime(year, month, d, 12, 0, 0)
utc_dt    = target_dt - timedelta(hours=numeric_tz)
jd_now    = swe.julday(utc_dt.year, utc_dt.month, utc_dt.day,
                       utc_dt.hour + utc_dt.minute/60.0)

sun_long  = swe.calc_ut(jd_now, swe.SUN,  calc_flags)[0][0]
moon_long = swe.calc_ut(jd_now, swe.MOON, calc_flags)[0][0]

If either calc_ut raises, the day is silently continued — it simply never appears in the output, with no error surfaced.

4Per day

Derive the three Panchang limbs

views.py:1035–1040

Only three of the five limbs are used. Yoga and Karana are never computed here.

elongation = (moon_long - sun_long) % 360
tithi_idx  = int(elongation // 12) + 1     # 1..30, capped at 30
nak_idx    = int(moon_long // (360/27)) % 27   # 0..26
weekday_idx = target_dt.weekday()          # Mon=0 .. Sun=6
  • Tithi — Moon-minus-Sun elongation in 12° steps. 1–15 is Shukla Paksha, 16–30 is Krishna Paksha. This is an absolute 1–30 index, not a paksha-relative 1–15 one. That distinction turns out to matter a great deal (see Finding 1).
  • Nakshatra — Moon longitude in 13°20′ steps, zero-indexed: 0 = Ashwini … 26 = Revati.
  • Vara — Python's weekday(), so Monday is 0. The avoid_varas lists and the Choghadiya table both use this same convention consistently.
5Per day

Divide the daylight into eight Choghadiya

views.py:904–932, 1044–1056

Sunrise and sunset come from swe.rise_trans with BIT_DISC_CENTER. Daylight is split into eight equal parts, each named by the weekday's Choghadiya rotation. Slots typed auspicious are collected, then truncated to the first three:

day_length_sec = (sunset - sunrise).total_seconds()
part_duration  = day_length_sec / 8

for i, ch_name in enumerate(choghadiya_order):
    if self.CHOGHADIYA_TYPES[ch_name] == "auspicious":
        start = sunrise + timedelta(seconds=i * part_duration)
        end   = start + timedelta(seconds=part_duration)
        auspicious_times_list.append(f"{start:%H:%M} - {end:%H:%M}")

auspicious_times_list = auspicious_times_list[:3]   # hard cap

This list is built before and outside the category loop — which is precisely why every category sharing a date shares its times.

6Per day

Apply the three gates per category

views.py:1058–1073

A plain conjunction — all three must hold, with no weighting, scoring or ranking:

is_suitable = True
if weekday_idx in rules["avoid_varas"]: is_suitable = False
if tithi_idx not in rules["tithis"]:    is_suitable = False
if nak_idx  not in rules["naks"]:       is_suitable = False

if is_suitable:
    moohrats_payload[category][month_name][date_str] = auspicious_times_list

Gate A · Vara

weekday_idx ∉ avoid_varas

Weekday blacklist. Tuesday (1) is excluded by ten of the eleven categories; Saturday and Sunday by several.

Gate B · Tithi

tithi_idx ∈ tithis

Lunar-day whitelist. Every category's list stops at 15, so this gate also acts as an unintended Paksha filter.

Gate C · Nakshatra

nak_idx ∈ naks

Lunar-mansion whitelist, 9–16 of the 27 permitted depending on category. The most selective gate in practice.

§ 4

How the clock windows are built

Seven Choghadiya names rotate across the eight daylight slots, so the eighth slot always repeats the first. Each name carries a fixed quality; only the three types marked auspicious are eligible.

§ 6

Findings

Behaviours in the current implementation that are worth a decision — some are almost certainly bugs, others may be deliberate simplifications that should simply be documented for API consumers.

Bug

1 · Krishna Paksha can never produce a muhurat

tithi_idx is computed on the absolute 1–30 scale, but the largest value in any category's tithis list is 15. Every one of the ~15 Krishna Paksha days in every month therefore fails Gate B unconditionally, for all 11 categories.

The rule lists read as paksha-relative tithis (1–15), which is how almanacs normally express them. If that was the intent, the comparison needs a paksha-relative index:

# current — absolute 1..30
tithi_idx = int(elongation // 12) + 1

# paksha-relative 1..15, if that is what the rules mean
tithi_rel = (int(elongation // 12) % 15) + 1

Treat this as a product decision, not just a code fix: it roughly doubles the number of dates returned. Traditional practice does permit many muhurats in Krishna Paksha tithis 1–10, so the current output is materially narrower than a printed panchang would give.

Bug

2 · Time windows run backwards east of about UTC+7

_get_sunrise_sunset starts its search at 00:00 UT on the UTC-shifted date. When the timezone offset exceeds the local sunrise hour, that start point is already past sunrise, so rise_trans returns the next day's sunrise while set_trans returns the current day's sunset. day_length_sec goes negative and every window is emitted end-before-start.

Bangkok +7.0   rise 11-21 06:21   set 11-20 17:46    -12.59 h   broken
Tokyo   +9.0   rise 11-21 06:24   set 11-20 16:31    -13.89 h   broken
Sydney  +11.0  rise 11-21 05:42   set 11-20 19:40    -10.03 h   broken
NewYork -5.0   rise 11-20 06:50   set 11-20 16:33     +9.72 h   ok

Tokyo output:  "04:39 - 02:55", "02:55 - 01:11", "23:27 - 21:43"

India and everywhere west of it is unaffected, which is why this has gone unnoticed. The fix is to anchor the search at local midnight expressed in UT — swe.julday(...) on the local date, minus the offset as a fractional hour — rather than at 0.0 UT of the shifted date.

Design

3 · Tithi and nakshatra are sampled once, at local noon

Both limbs are read at a single instant. A nakshatra that ends at 09:00 or begins at 15:00 is invisible to the filter, and the Moon can traverse a full nakshatra boundary within a day. The returned time windows are never checked against the limb that qualified the date — a date can be returned whose auspicious Choghadiya fall entirely outside the qualifying nakshatra.

Traditional muhurat selection resolves the limb over the actual window. Making that change means computing nakshatra and tithi intervals — the machinery already exists in _find_next_boundary on the Panchang view (views.py:117) and could be reused here.

Design

4 · The returned times are identical for every category

auspicious_times_list is computed once per day, outside the category loop, and the same list object is assigned to every qualifying category. A Vivah muhurat and a Vahan Puja muhurat on the same date get byte-identical windows. Consumers should not read the times as category-specific guidance — they are simply "that day's auspicious Choghadiya".

Design

5 · Rahu Kaal is not excluded

The Panchang endpoint computes an Abhijit-vs-Rahu-Kaal overlap and emits an explicit warning string (views.py:339–381). This endpoint does no such check — a returned window can sit wholly inside Rahu Kaal. Rahu Kaal is also an eighth-of-daylight slot, so the two grids align exactly and the intersection is cheap to compute; the mapping already exists as rahu_parts_mapping.

Note

6 · The [:3] cap silently drops a valid slot on three weekdays

Monday, Wednesday and Thursday each have four auspicious Choghadiya; the fourth — the slot-7 repeat, running until sunset — is truncated away. Tuesday, Friday, Saturday and Sunday are unaffected, so the cap only ever bites on those three weekdays.

Note

7 · One UTC offset is used for the whole month

The offset is resolved once, against the synthetic date YYYY-MM-01. A DST transition mid-month leaves every subsequent day off by an hour. Irrelevant for India, but wrong for European and North American locations in March, October and November.

Note

8 · Failures are swallowed, not surfaced

Three independent silent-fallback paths: an ephemeris error continues the day out of the response; a rise_trans failure substitutes a hardcoded 06:00 / 18:30 day; and an unresolvable location falls back to Ujjain with only a print() to stdout. Since the response echoes no location, a caller who mistypes a city receives Ujjain timings with no indication anything went wrong.

Only Finding 2 produces visibly malformed output. Findings 1 and 3–5 produce output that looks perfectly well-formed but encodes a narrower or different notion of "auspicious" than a printed panchang would. Those are the ones to align on with whoever owns the astrological rules before changing any code.
